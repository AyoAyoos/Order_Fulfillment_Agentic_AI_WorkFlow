JURY Q1: WHY IS SHIPPING CALCULATED AFTER INVENTORY?
================================================================================
Because shipping is a meaningful step that should only run when the order can
actually be fulfilled. If we computed shipping BEFORE checking stock, we would
spend effort (and charge a customer) for a delivery that cannot happen.

Look at the NODES RUN of the DECLINE path:
    [check_inventory] -> [decline_order]

calculate_shipping is NEVER reached. So when kokum_sherbet is out of stock,
the graph declines the whole order BEFORE any shipping/billing happens — the
billing section prints "No billing was produced and NO shipping was charged."

If shipping came first, the graph would instead read:
    [check_inventory] -> [calculate_shipping] -> [decline_order]
which would leave a shipping_cost on a declined order — wrong.

================================================================================
JURY Q2: HOW IS decline_order TRIGGERED? (walk through the condition)
================================================================================
1) The graph ALWAYS starts at the check_inventory node (the entry point).
2) check_inventory loops over EVERY dish in the order (items list) and tests
   THE CONDITION for each one:

        is_stock_enough = (stock_in_database >= quantity_requested)

   For the DECLINE trace:
     - 2x misal_pav:   stock=30 >= 2  -> True  (OK)
     - 4x kokum_sherbet: stock=0  >= 4  -> False (INSUFFICIENT)
   It records all_ok=False and remembers failed_item='kokum_sherbet'.

3) When check_inventory finishes, LangGraph automatically calls the
   conditional-edge function route_after_inventory(state). That function looks
   at the single bool we saved:

        if inventory_ok is True:  return "sufficient"   -> calculate_shipping
        else:                     return "insufficient" -> decline_order

4) Because ONE dish (kokum_sherbet) was short, inventory_ok=False, so the edge
   returns "insufficient" and LangGraph routes to decline_order.
   This is ALL-OR-NOTHING: the 2x misal_pav was fine, but the whole order is
   still declined because we cannot accept partial orders — one short item
   kills the entire order.
